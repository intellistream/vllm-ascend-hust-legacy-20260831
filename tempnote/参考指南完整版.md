1. Concepts & Background
What are we doing?
The vLLM-HUST forks (vllm-hust, vllm-ascend-hust) diverged from upstream
(vllm-project/vllm, vllm-project/vllm-ascend) around early May 2026.
Since then, ~2,000 upstream PRs have been merged that we don't have.
Our goal is to selectively bring upstream changes into our forks without
breaking Ascend-specific functionality.
Key terms
Term
Meaning

upstream
The original vllm-project/* repositories

fork
Our vLLM-HUST/* repositories

topic pack
A group of PRs classified by module area (e.g., VLLM-CI, ASC-CORE)

strategy
pick (merge now), pick-later (needs validation), ignore (skip)

sync branch
A <github-id>/sync-* branch where we stage upstream changes before creating a PR

Repository layout
vllm-hust (fork)                    vllm-project/vllm (upstream)
  origin → git@github.com:            origin → git@github.com:
    vLLM-HUST/vllm-hust.git             vllm-project/vllm.git
  main branch                         main branch
  ~1460 PRs behind ←────────────────── ~1460 new PRs

vllm-ascend-hust (fork)             vllm-project/vllm-ascend (upstream)
  origin → git@github.com:            origin → git@github.com:
    vLLM-HUST/vllm-ascend-hust.git     vllm-project/vllm-ascend.git

3. Strategy Overview: When to Merge vs Cherry-pick
Scenario
Method
Why

pick pack with 50+ PRs
Bulk merge (Method A)
Efficient; preserves history; fewer conflicts

pick pack with <10 PRs
Cherry-pick (Method B)
Precise; easy to review

pick-later pack
Cherry-pick (Method B)
Selective; skip PRs that don't apply to Ascend

Security fixes
Cherry-pick immediately
Must be applied ASAP regardless of pack

Entire upstream catch-up
Bulk merge in phases
Merge upstream tag-by-tag

Decision flowchart
Is it a security fix?
  ├─ YES → Cherry-pick it NOW (any method), create hotfix PR
  └─ NO ↓

Is the pack strategy mostly `pick`?
  ├─ YES, >30 PRs → Bulk Merge (Method A)
  ├─ YES, <30 PRs → Cherry-pick (Method B)
  └─ NO (mostly `pick-later`) → Cherry-pick selectively (Method B)---
4. Method A: Bulk Merge (for large pick batches)
Best for: VLLM-CI (223 PRs), VLLM-V1-CORE (309 PRs), ASC-TEST (131 PRs), etc.
Risk: Medium — may include some PRs you'd rather skip.
Mitigation: Review the diff before pushing; revert individual commits if needed.
Step-by-step
# 1. Start from latest fork main
git checkout main
git pull origin main

# 2. Create a sync branch (MUST use <github-id>/ prefix per branching policy)
#    Replace <github-id> with your actual GitHub username, e.g., zhangsan
git checkout -b <github-id>/sync-vllm-ci-week1

# 3. Merge upstream main into your sync branch
#    This brings ALL upstream changes; we'll refine later
git merge upstream/main --no-commit --no-ff

# 4. If there are conflicts, resolve them (see Section 6)
#    For now, if conflicts are too complex, you can abort:
#    git merge --abort

# 5. Review what changed — does it look reasonable?
git diff --stat HEAD           # Summary of all changes
git diff --stat HEAD | wc -l   # How many files changed

# 6. If you want to EXCLUDE certain files (e.g., CUDA-only changes):
#    Restore specific files to their pre-merge state:
git checkout HEAD -- csrc/cutlass/        # Example: skip CUDA kernel
git checkout HEAD -- rust/                # Example: skip Rust frontend

# 7. Commit the merge
git add -A
git commit -m "sync: merge upstream vllm main into vllm-hust (CI pack)

Merged upstream changes up to $(date +%Y-%m-%d).
Pack: VLLM-CI (CI / Build / Docker)
Strategy: pick

Changes excluded:
- csrc/cutlass/ (CUDA-only kernels)
- rust/ (Rust frontend, not relevant to Ascend)

See: /workspace/hust-work/vllm/upstream-sync-analysis/packs/vllm/VLLM-CI.md"

# 8. Push and create PR
git push origin <github-id>/sync-vllm-ci-week1Alternative: Merge up to a specific upstream commit
If you don't want ALL of upstream (e.g., you want to stop before a certain date):
# Find the upstream commit just before a certain date
git log upstream/main --before="2026-05-15" --oneline | head -1
# Output: abc1234 [Bugfix] Fix something (#42000)

# Merge up to that commit (inclusive)
git merge abc1234 --no-commit --no-ffAlternative: Merge up to an upstream release tag
# List upstream tags
git tag -l --sort=-version:for-each-ref 'refs/tags/v*' | head -10

# Merge up to a specific tag
git merge v0.9.0 --no-commit --no-ff---
5. Method B: Cherry-pick (for selective pick-later PRs)
Best for: VLLM-QUANT (93 PRs, pick selectively), ASC-CORE (55 PRs), etc.
Risk: Low — you pick exactly what you want.
Downside: Slower; more merge conflicts between cherry-picks.
Step-by-step: Single PR
# 1. Start from latest fork main
git checkout main
git pull origin main

# 2. Create a sync branch
git checkout -b <github-id>/sync-asc-core-bugfixes

# 3. Fetch upstream (in case you haven't recently)
git fetch upstream main

# 4. Cherry-pick a specific upstream commit
#    First, find the commit hash in upstream:
git log upstream/main --oneline --grep="Fix worker" | head -5
#    Output: def5678 [Bugfix] Fix worker init for multi-node (#43210)

#    Cherry-pick it:
git cherry-pick def5678

# 5. If there's a conflict, resolve it (see Section 6)

# 6. Repeat for more PRs in the same pack
git cherry-pick abc1234
git cherry-pick 98765ab
# ... etc

# 7. Push and create PR
git push origin <github-id>/sync-asc-core-bugfixesStep-by-step: Batch of PRs from a pack document
Each pack document (e.g., packs/vllm-ascend/ASC-CORE.md) has a "Suggested Merge Order"
section with PRs grouped into batches. Here's how to apply a batch:
# 1. Read the pack document, find Batch 1 (e.g., "Bug fixes (27 PRs)")
# 2. Extract PR numbers from the table
# 3. For each PR, find the merge commit in upstream:

# Example: PR #9049 in vllm-ascend
git log upstream/main --oneline --grep="#9049" | head -1
# Output: aaa1111 [BugFix] Use non-device-specific triton pow (#9049)

# 4. Cherry-pick the merge commit
git cherry-pick aaa1111

# 5. If a cherry-pick fails with conflicts:
#    - Try to resolve (see Section 6)
#    - If too complex, skip and note it for manual review:
git cherry-pick --skip
echo "SKIP: PR #9049 — conflict too complex, needs manual review" >> /tmp/skip-log.txt

# 6. Continue with next PRs in the batchShortcut: Cherry-pick a range of commits
If the pack's PRs are contiguous in upstream history:
# Find the first and last commit in the range
git log upstream/main --oneline --after="2026-05-08" --before="2026-05-16" | tail -1
# Output: first111 [BugFix] ... (#9049)

git log upstream/main --oneline --after="2026-05-08" --before="2026-05-16" | head -1
# Output: last9999 [Feature] ... (#9656)

# Cherry-pick the entire range (oldest first)
git cherry-pick first111^..last9999
# Note: the ^ means "include this commit too"---
6. Conflict Resolution
Conflicts are expected when syncing 2K PRs. Here's how to handle them.
6.1 Understanding conflict markers
When a conflict occurs, git marks the conflicting sections:
<<<<<<< HEAD
# This is YOUR fork's version (current code)
def process_request(req):
    return ascend_specific_handler(req)
=======
# This is UPSTREAM's version (new code)
def process_request(req, ctx=None):
    return new_handler(req, ctx)
>>>>>>> upstream/main6.2 Resolution strategy
Situation
Action

Upstream added a new function, no conflict
Accept upstream (keep both)

Upstream modified a shared function
Merge carefully: keep Ascend-specific logic + upstream improvements

Upstream change is CUDA-only
Keep your fork's version (discard upstream)

You're not sure
Keep your fork's version and flag for review

6.3 Practical resolution workflow
# 1. See which files conflict
git diff --name-only --diff-filter=U

# 2. For each conflicting file, open it in your editor
#    Search for <<<<<<< markers

# 3. Common patterns:

# Pattern A: Upstream added imports you need
# → Keep the upstream imports, ensure they work on Ascend

# Pattern B: Upstream changed function signature
# → Adapt: keep Ascend behavior but update the signature

# Pattern C: Upstream change is purely CUDA-specific
# → Keep your fork's version:
git checkout --ours path/to/file.py
git add path/to/file.py

# Pattern D: You want upstream's version entirely
git checkout --theirs path/to/file.py
git add path/to/file.py

# 4. After resolving all conflicts in a file:
git add path/to/file.py

# 5. After resolving ALL conflicts:
#    For merge:
git commit    # Complete the merge

#    For cherry-pick:
git cherry-pick --continue6.4 When to abort and ask for help
# If conflicts are too complex (>10 files, or core architecture changes):
git merge --abort        # For Method A
git cherry-pick --abort  # For Method B

# Then:
# 1. Note the pack and PR numbers in the sync log
# 2. Ask the pack owner or core engineer for help
# 3. Provide: pack name, PR numbers, conflict files---

10. Troubleshooting
Q: "fatal: refusing to merge unrelated histories"
# This means the fork and upstream have diverged too much.
# Use --allow-unrelated-histories flag:
git merge upstream/main --allow-unrelated-histories --no-commitQ: Cherry-pick says "empty commit"
# The change may already be in your fork. Skip it:
git cherry-pick --skipQ: Too many conflicts in a bulk merge
# Abort and switch to cherry-pick method:
git merge --abort

# Then cherry-pick the most important PRs individually:
git cherry-pick <commit-hash>Q: "error: could not apply  ..." during cherry-pick
# This is a conflict. See Section 6 for resolution.
# Quick options:
git checkout --ours path/to/file    # Keep fork's version
git checkout --theirs path/to/file  # Keep upstream's version
# Then: git add path/to/file && git cherry-pick --continueQ: After merge, some Ascend-specific code is gone
# Restore the file from your fork's pre-merge state:
git log --oneline -5    # Find the commit BEFORE the merge
git checkout <pre-merge-hash> -- path/to/ascend-file.py
git add path/to/ascend-file.py
git commit --amend      # Add the restoration to the merge commitQ: How do I find the upstream commit for a PR number?
# Search by PR number in commit message:
git log upstream/main --oneline --grep="#42000" | head -1

# Or search by title keywords:
git log upstream/main --oneline --grep="Fix worker init" | head -3Q: My sync branch is behind upstream again (new PRs landed during my work)
# Re-fetch and re-merge:
git fetch upstream main
git merge upstream/main --no-commit
# Resolve any new conflicts, commit, push---
