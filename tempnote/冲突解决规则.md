# 冲突解决规则

## 同步工作流

### 一、流程初始化
1. **开始**：流程触发。
2. **获取上游 PR 列表**：数据来源为 pack 文档或 API。

### 二、核心判定与分支处理

执行"安全补丁？"条件判断：

- **路径 A：判定为"是"** → 执行"立即 Cherry-pick（单独热修复 PR）"
  - 热修复 PR 绕过常规代码合并，直接汇入测试验证环节

- **路径 B：判定为"否"** → 进入"按策略分类 PR"节点，分三个子策略：

| 策略 | 状态 | 操作 |
|------|------|------|
| 批量合并 | Pick | `git cherry-pick` 逐条合并 |
| 选择性 Cherry-pick | Pick-later | 延后逐个 `git cherry-pick` |
| 跳过 | Ignore | 标记已忽略，不合并任何代码，此分支终止 |

### 三、冲突处理

由"批量合并"与"逐个 Cherry-pick"两条路径汇合后，执行"有冲突？"判断：

- **是** → 解决冲突（编辑文件 → git add → continue）→ 流向"继续"
- **否** → 直接流向"继续"

### 四、测试与收尾

常规合并路径与热修复路径汇合，依次执行：
1. **测试验证**：导入测试 / CI 运行
2. **提交同步 PR**：推送到 origin，创建 PR
3. **完成**：流程结束

## 冲突决策流程

```
冲突出现
  ├── modify/delete 冲突
  │     ├── HEAD 删了，upstream 改了 → git rm（保留删除）
  │     └── upstream 删了，HEAD 改了 → 保留 HEAD
  │
  └── content 冲突
        ├── 双方都添加了不同内容 → 🔧 手动合并，都保留
        ├── HEAD 有定制，upstream 是通用改动 → --ours
        ├── upstream 纯新增，HEAD 无相关内容 → --theirs
        ├── 涉及版本号/产品名变更 → 🔍 待确认
        └── 不确定 → 报告用户决策
```

## 铁律

1. **每个冲突必须先分析再处理**，不得跳过直接 `--ours`/`--theirs`
2. **"手动合并"** = 人工编辑冲突文件，不是选 `--ours` 或 `--theirs`
3. **涉及 HUST 环境特定内容**（版本号、产品名、硬件配置）→ 必须确认
4. **不确定时优先保护 HEAD**

## 常用 Git 操作

```bash
# 查看冲突文件
git status --short

# 查看冲突内容
grep -n -B3 -A10 "<<<<<<< HEAD\|=======\|>>>>>>>" <file>

# resolve modify/delete (HEAD deleted)
git rm <file>

# resolve content (保留 HEAD)
git checkout --ours <file>
git add <file>

# resolve content (采用 upstream)
git checkout --theirs <file>
git add <file>

# 继续 cherry-pick
git cherry-pick --continue --no-edit

# 跳过
git cherry-pick --skip

# 放弃
git cherry-pick --abort
```
